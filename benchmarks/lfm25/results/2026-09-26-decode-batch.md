**Shared GPU, and it shows.** Every run shared zorak with other work. The two timing runs reported: run B (13:10, under `zorak-heavy.lock`; rocm-smi showed only the deployed lfm2d pod beside us, yet batch-1 read 11-12 ms against 9.5 in run A, so host or pod load was present) and run A (13:03; quiet for ctx16 and ctx512, then another agent's `chat_real` test joined, so its ctx2048 B >= 16 and mixed rows are contaminated). Treat absolute numbers as +-20%; the batched-vs-serial ratio is measured within a run, minutes apart.

## Throughput

Per-step wall time includes reading each row's greedy token back to the host. 3 warm-up steps, 24 timed. Serial = the same rows, one batch-1 `forward` each, 12 timed steps. ctxN regimes use N-token states (rows beyond the distinct prompts are clones, forked on the first warm-up step); mixed uses every prompt at full length (256-3072, so its mean context depends on B).

Reading: one batched step moves a row by at most 0.15 nats at the top-1 token (KL <= 0.045); with FORCE_DMMV, whose dense projections avoid the q8_1 requantization, by <= 0.045 nats, so most of the one-step difference is the activation requantization that MMVQ/MMQ do and DMMV does not. Over 8 steps the difference compounds through each path's own KV, and a few rows jump (KL up to 1.6, one >= 1% token 6.8 nats at B=8) — consistent with MoE routing flips at near-ties, which a small perturbation can trigger; FORCE_DMMV shows the same jumps at B >= 16 (1.9 nats). `rocm_rows_are_position_invariant_over_several_steps` shows these are not row mixing: reversing the batch reverses the logits bit for bit over six steps. The drift numbers are deterministic (identical across the shared-GPU runs).

CPU reference (tiny F32 fixture, `tests` in batch.rs): batched and batch-1 logits are equal (max |delta| 0), state included; asserted to 1e-5.
